# N2 — Purchase quantity has no upper limit (2,147,483,648 accepted)

| Field | Value |
| --- | --- |
| Component | `POST /transactions/new-purchase/` (`Purchase.quantity`, `PurchaseForm`) |
| Severity | Major |
| Priority | P2 |
| Status | Open |
| Breaks | Assumption A1 (purchase quantity at most 100000); shared record `Item.quantity` |
| Found by | `test_purchase.py` (Member 2) |

## Steps to reproduce

1. Log in as `manager`.
2. Create an item with stock 46 (or use any item).
3. POST `/transactions/new-purchase/` with `quantity=2147483648`, `price=1.00`, `delivery_status=S` and a valid item, vendor and CSRF token.
4. Open the product page.

## Expected

The form is rejected (quantity above 100000) and stock stays 46.

## Actual

302 (saved). Stock becomes **2,147,483,694**. `quantity` only has `MinValueValidator(1)`. On SQLite this is stored; on PostgreSQL (`DB_HOST` set, as in production) `Item.quantity` is a 32-bit integer whose maximum is 2,147,483,647, so the stock update would overflow and fail with a server error.

## Evidence

- Test: `tests/team/api/test_purchase.py::test_purchase_above_int32_rejected_N2`
- `reports/api/run-baseline.txt` line 30: `N2: quantity 2147483648 accepted (A1 max is 100000); stock is now 2147483694`

## Triage decision

Fix. Add `MaxValueValidator(100000)` to `Purchase.quantity` (and the form widget `max`). Corrupts the shared stock record and breaks on the production database, so it goes before release. Candidate for root cause analysis.
