# N6 — Item id beyond 64 bits gives 500 instead of 400

| Field | Value |
| --- | --- |
| Component | `POST /transactions/new-sale/` (`create_sale`, `Item.objects.filter(pk__in=...)`, `transactions/services.py:91-94`) |
| Severity | Minor |
| Priority | P3 |
| Status | Open |
| Breaks | FR3 (an unknown item is rejected with a clear message and nothing is saved); BR1 (no upper bound on ids) |
| Found by | `test_api_coverage.py`, while covering the 500 response (Member 2) |

## Steps to reproduce

1. Log in as `cashier`; take a CSRF token from `/transactions/new-sale/`.
2. POST a valid sale whose `items` also contains `{"id": 9223372036854775808, "quantity": 1}` (2**63).

## Expected

400 `"One or more items no longer exist."`. The same body with a too-large **customer** id already gets the correct 400 `"Select a valid customer."`.

## Actual

500 `{"status": "error", "message": "The sale could not be saved. Please try again."}`. SQLite cannot bind an integer above 2**63−1 in the `pk__in` query (`OverflowError`), and the view's catch-all handler turns this into a 500. Nothing is saved: the error happens inside the transaction, and the test confirms stock is unchanged.

## Evidence

- Test: `tests/team/api/test_api_coverage.py::test_item_id_beyond_64_bit_gives_500_and_saves_nothing`. It passes by design: it records the observed 500 and checks that stock is unchanged.
- The customer-id counterpart `test_customer_id_beyond_64_bit_is_rejected_cleanly` passes with 400.
- `reports/api/results-baseline.xml`: both testcases are listed as passed.

## Triage decision

Fix, low priority. Add an upper bound in `_int` (or in `parse_lines`) for ids, for example 1..2**63−1, and return the normal 400. No data risk; only a misleading 500 and an error-level log entry.
