# N4 — The same sale sent twice is recorded twice

| Field | Value |
| --- | --- |
| Component | `POST /transactions/new-sale/` (`sale_create_view`, `create_sale`) |
| Severity | Major |
| Priority | P2 (was P1; lowered 28 Nov 2026 after UI evidence) |
| Status | Open |
| GitHub Issue | [#4](https://github.com/Malaikaa0/sales-and-inventory-management/issues/4) |
| Breaks | Assumption A3 (a repeated identical request records one sale and reduces stock once); FR2 (a completed sale reduces stock by the quantity sold) |
| Found by | `test_repeats.py` (Member 2) |

## Steps to reproduce

1. Log in as `cashier`; note an item's stock (product page).
2. POST the same JSON body to `/transactions/new-sale/` twice in a row (for example a double click or a client retry after a timeout).
3. Read the stock back.

## Expected

One sale; stock reduced once. The second request is either answered with the first sale or rejected as a duplicate.

## Actual

Two sales are created (sale ids 122 and 123 in the latest run) and stock is reduced twice. The view has no idempotency key and no duplicate check.

## Evidence

- Test: `tests/team/api/test_repeats.py::test_same_sale_posted_twice_records_one_sale`
- `reports/api/run-baseline.txt` line 55: `AssertionError: duplicate sale recorded: [122, 123]`

## Triage decision

Fix. Accept an idempotency key from the till (a UUID per checkout), store it on `Sale` with a unique constraint, and return the existing sale on a repeat. Customers are charged twice and stock is wrong, so this was first set to P1 (lowered to P2, see the update below). Candidate for root cause analysis.

## Update 28 Nov 2026: behaviour in the browser

The till page prevents the ordinary double submit. `pos.js` disables **Complete sale** as soon as the request starts (`button.disabled = true`, line 254). The Playwright test `tests/team/e2e/test_e2e_m2_use_cases.py::test_uc_m2_2_exc6_double_click_records_one_sale` double-clicks the button and confirms one sale and one stock reduction (passes, `reports/e2e/run-m2.txt`).

N4 therefore happens with repeated direct API requests (client retries, scripts, integrations). It can still happen through the till in one case. On a network error the `.catch`/`.finally` handler re-enables the button (lines 281–285). If the first request was saved but its response was lost, the cashier's second click records a second sale.

**Severity / priority re-check:** severity stays **Major**: when it happens, the customer is charged twice and stock is wrong. Priority drops from **P1 to P2**: the common path (double click) is blocked, and the remaining paths need a lost response or a direct API client. Triage decision confirmed: issue #4 relabelled `priority:P2`, severity stays `severity:major`.
