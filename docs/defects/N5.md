# N5 — Boolean false is accepted as 0 for tax, amount paid and points

| Field | Value |
| --- | --- |
| Component | `POST /transactions/new-sale/` (`transactions/services.py:74,77,80`) |
| Severity | Minor |
| Priority | P3 |
| Status | Open |
| Breaks | Assumption A5 (a boolean is the wrong type and is rejected); BR1 |
| Found by | Generated EP cases `*-EP-wrong-type-bool-false` (Member 2) |

## Steps to reproduce

1. Log in as `cashier`; take a CSRF token from `/transactions/new-sale/`.
2. POST a valid sale with `"tax_percentage": false` (or `"redeem_points": false`, or `"amount_paid": false`).

## Expected

400 with "Tax must be a number." / "Points to redeem must be a whole number." / "Amount paid must be a number."

## Actual

- `tax_percentage: false` → 200, the sale is saved with 0% tax.
- `redeem_points: false` → 200, saved with no redemption.
- `amount_paid: false` → 400, but with the wrong reason ("Amount paid (0.00) is less than the total (1.00).").

The code reads `tax_percentage or 0`, so every falsy value, including `false`, silently becomes 0. `true` is rejected correctly.

## Evidence

- `reports/api/run-baseline.txt` line 175: `SALE-tax_percentage-EP-wrong-type-bool-false: expected 400, got 200`
- line 150: `SALE-redeem_points-EP-wrong-type-bool-false: expected 400, got 200`
- line 92: `assert 'Amount paid must be a number.' in 'Amount paid (0.00) is less than the total (1.00).'`
- Tests: `tests/team/api/test_sale_generated.py::test_generated_sale_case[SALE-{tax_percentage,redeem_points,amount_paid}-EP-wrong-type-bool-false]`

## Triage decision

Fix, low priority. Replace `value or 0` with an explicit `None`/`""` default and reject `bool` before converting. The till never sends booleans, so the risk is limited to other API clients (a buggy client could record sales with no tax).
