# N1 — Quantity above the maximum gets the "at least 1" message

| Field | Value |
| --- | --- |
| Component | `POST /transactions/new-sale/` (`transactions/services.py:61-62`) |
| Severity | Minor |
| Priority | P3 |
| Status | Open |
| Breaks | Assumption A4 (message names the upper limit), BR1 (quantity 1..100000) |
| Found by | Generated BVA case `SALE-items[].quantity-BVA-max+d` (Member 2) |

## Steps to reproduce

1. Log in as `cashier` (password `demo-pass-123`) on a server seeded with `seed_demo`.
2. Take a CSRF token from `GET /transactions/new-sale/`.
3. POST to `/transactions/new-sale/` with `X-CSRFToken` and JSON
   `{"customer": <id>, "items": [{"id": <item>, "quantity": 100001}], "tax_percentage": 0, "amount_paid": 1000000}`.

## Expected

400 with a message that names the limit, for example "Quantity cannot be more than 100000."

## Actual

400 with `"Quantities must be at least 1."`. The rejection is correct, but the message describes the lower bound, so the cashier is told the wrong thing.

## Evidence

- Test: `tests/team/api/test_sale_generated.py::test_generated_sale_case[SALE-items[].quantity-BVA-max+d]`
- `reports/api/run-baseline.txt` line 126: `assert '100000' in 'Quantities must be at least 1.'`

## Triage decision

Fix. One condition (`qty < 1 or qty > MAX_QTY_PER_LINE`) shares one message; split it into two messages. Low risk, low priority: the sale is still rejected and stock is safe.
